# CLAUDE.md — рабочие инструкции и стандарты кода

Проект: лендинг «Продажа графитовых лопаток» на **Symfony 7.4 LTS (backend) + React/Vite (frontend)**, PHP 8.5, MySQL 8.4.
Деплой на BeGet: фронт собирается локально, на сервер заливаются готовые файлы (см. `docs/deploy-beget.md`).

---

## Общие правила работы

- Перед удалением/перезаписью файла — посмотреть, что внутри.
- Коммитим/пушим только по запросу пользователя. Работа — в ветке, не в `master`.
- Не выдавать сделанным то, что не проверено. Тесты упали — так и сказать.

## Пользователь

### Не знает React (и слабо — современный бэк)

Объяснять **как в детском саду**, особенно фронтенд:
- Любой новый термин/концепт React (компонент, хук, пропсы, state, JSX, роутинг) — пояснять при первом появлении 1–2 предложениями человеческим языком, можно с бытовой аналогией.
- Не считать ничего «очевидным». Если завёл новый файл/папку/команду — сказать зачем она и что делает.
- Show, don't assume: давать конкретные команды для запуска и что должно появиться на экране.
- Лучше написать больше пояснений, чем меньше — пользователь специально закладывает время на вникание.

## Безопасность (критично — на этих граблях стоял старый сайт)

**НЕЛЬЗЯ:**
- Хардкодить секреты (DB-пароли, API-ключи, reCAPTCHA secret) в коде или коммитить в git. Только `.env.local` / Symfony secrets vault.
- Хранить или сравнивать пароли в открытом виде. Только `password_hasher` (argon2id).
- Конкатенировать пользовательский ввод в SQL. Только Doctrine / параметризованные запросы.
- Эхать `$_POST`/ввод в ответ без экранирования (XSS).
- Самопальная аутентификация (cookie id+md5(hash)). Только Symfony Security.
- Операции с файлами по пользовательскому пути (старый `search` грепал файлы — path traversal).

**НУЖНО:**
- Все секреты — через env / vault, в `.gitignore`.
- Валидация входных данных на бэке (Symfony Validator / `#[Assert\*]`), не доверять фронту.
- CSRF-защита на мутациях, CORS настроен явно под нужный origin.
- Cookie сессии: `HttpOnly`, `Secure`, `SameSite`.
- reCAPTCHA проверяется на сервере, не на клиенте.

## Локальная разработка — только Docker

- Хост-PHP/composer/node **не используем**. Всё крутится в контейнерах (`compose.yaml`): `php` (8.5-fpm + расширения), `nginx` (docroot `backend/public`, сайт на http://localhost:8083), `db` (MySQL 8.4, с хоста порт 3308), `node` (Vite на http://localhost:5175).
- Команды — через `Makefile`: `make init` (первый запуск), `make up` (поднять), `make sh` (войти в php), `make composer c="..."`, `make console c="..."`. Или напрямую `docker compose ... --user dev`.
- PHP-команды (composer, bin/console) запускать **внутри контейнера под пользователем `dev`** (uid 1000), чтобы файлы не были root.
- Прод (BeGet shared) Docker не использует — там обычный PHP-FPM. Локальный Docker лишь повторяет стек (nginx + php-fpm + mysql) для паритета.
- Деплой: `make deploy` из `master` — сборка фронта локально, `git push`, на сервере `git pull` + `scripts/deploy-remote.sh`, затем `rsync` готового фронта. Node на сервере не используется.

## Backend — PHP / Symfony 7.4

- **PHP 8.5**, `declare(strict_types=1);` в каждом файле.
- Стандарт: **PSR-12**, проверка `php-cs-fixer` (Symfony ruleset). Статанализ — **PHPStan** (level max или близко).
- Типизировать всё: аргументы, возвраты, свойства. Никаких `mixed` без причины. Использовать enums, readonly, named args, constructor property promotion.
- **Никаких коротких тегов** `<?` / `<?=` в PHP-логике (старый код грешил `<?require`).
- Архитектура: тонкие контроллеры, бизнес-логика в сервисах. DI через autowiring, без `new` сервисов руками. `final` для классов по умолчанию.
- Doctrine: атрибуты для маппинга (не XML/YAML), миграции через `doctrine/migrations` (схему руками не правим).
- API: ответы — JSON через Serializer, единый формат ошибок. HTTP-коды по смыслу (200/201/400/401/403/404/422).
- Именование: классы `PascalCase`, методы/переменные `camelCase`, эндпоинты `kebab/snake` в URL (`/api/posts`).
- Каждый PHP-файл — один класс, namespace по PSR-4 (`App\...`).

## Кэш и логи

- `backend/var/cache/` и `backend/var/log/` — в git не коммитим (уже в `.gitignore`).
- После изменения конфигурации чистить кэш: `php bin/console cache:clear` (в контейнере под `dev`).
- Логи — только через PSR-3 `LoggerInterface` (инжектить в сервис). Никаких `error_log()`, `echo`, `file_put_contents` в лог-файл руками (так делал старый сайт).

## Базы данных и миграции

СУБД проекта — **MySQL 8.4** (локально контейнер `db`, прод — MySQL на BeGet). PostgreSQL/ClickHouse в проекте нет.

- Маппинг — атрибутами Doctrine; схему БД руками не правим, только через миграции.
- Неймспейс миграций: `DoctrineMigrations` (дефолт Symfony).
- Миграцию создавать на **каждое** изменение схемы (`make console c="make:migration"`), применять `doctrine:migrations:migrate`.
- **Проверять сгенерированную миграцию перед коммитом** — Doctrine иногда генерит лишний/неверный SQL.
- **Не редактировать уже смерженные миграции.** Нужна правка — новая миграция сверху.
- Повторного применения бояться не нужно: Doctrine хранит применённые версии в `doctrine_migration_versions` и не гоняет их дважды. MySQL **не** поддерживает `IF NOT EXISTS` для `ADD COLUMN`/`CREATE INDEX` (это синтаксис PostgreSQL) — на него не закладываемся.
- Параметризованные запросы / QueryBuilder. Конкатенации ввода в SQL — никогда (см. раздел Безопасность).

## Кэширование

- Кэшировать дорогие запросы и вычисления через **Symfony Cache** (`CacheInterface`), а не самописными решениями.
- TTL подбирать по частоте изменения данных; инвалидировать кэш при изменении данных (по тегам, где уместно).

## API — документация

- Когда появится API: документация — **OpenAPI/Swagger через PHP-атрибуты** в коде (`nelmio/api-doc-bundle` + атрибуты `#[OA\...]`), а не отдельными YAML/руками.
- Держать описание эндпоинтов рядом с контроллером, чтобы доки не расходились с реализацией.

## Frontend — React / Vite

- **Функциональные компоненты + хуки**, без классовых.
- TypeScript. Типы для API-ответов.
- Компоненты `PascalCase`, файлы под компонент. Логику запросов вынести (хуки/сервис-слой), не дёргать `fetch` россыпью по компонентам.
- Линт: `make lint` (oxlint + проверка типов `tsc`).

## Тесты

- Автотесты в проекте **не пишем** (решение пользователя).
- Перед тем как сказать «готово» — `make lint`, `make front-build` и открыть сайт на http://localhost:8083.

## Коммуникация с агентами

При взаимодействии с AI-ассистентами и автоматизированными агентами (включая суб-агентов):
- Всегда **русский язык** — в обсуждениях задач, запросах, подтверждениях, промптах суб-агентам.
